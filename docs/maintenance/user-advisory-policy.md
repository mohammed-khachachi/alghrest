## Personal account and risk plan — 2026-10-11

The separately approved 24-file increment adds a **USER POLICY** financial
worksheet to the assistant. It follows the user's own rules, independently of
external progression/fee clarification: USD50,000 start, USD3,000 objective,
USD1,100 daily loss, USD2,000 EOD drawdown, best positive day **strictly less
than 30%** of total net profit, dated MES/MNQ only, 20 gross Micro across
positions and working orders, and entry **07:00 inclusive–14:00 exclusive UTC**.
Exact 30% does not complete the personal objective. There is no invented minimum
trading-day requirement. Consistency is a completion condition, not an entry halt.

`core.advisory.user_risk` owns personal ordering: revalidate the captured journal
and request; replay shared Decimal EOD/account arithmetic; reconcile current
revision/freshness and the existing gross cap; retain every recorded loss breach;
then calculate the flat-account stop budget. Legacy firm policy/risk interfaces
and financial calculations are unchanged. No historical journal is relabeled or
migrated. A matching legacy program tag does not establish personal or firm origin.
A journal with different financial terms is blocked; create a separate record
explicitly. The optional personal presentation does not change stored profile fields.

The EOD floor starts at USD48,000, ratchets using finalized net session balances,
and caps at USD50,000. Open-session PnL does not ratchet it. Touching the daily
loss boundary or drawdown floor is a breach; later recovery/date changes do not
clear it. Historical PnL/minima already include fees and are not charged twice.
The retained journal date changes at 17:00 America/Chicago; finalization still
requires the existing after-16:00 Chicago/flat-journal convention. Those storage
conventions do not impose an external permitted-hours gate on personal sizing,
and the 14:00 UTC entry cutoff never causes automatic liquidation.

Prospective fees must be explicit **round-trip USD per contract** and slippage
must be explicit points. Both require a reviewed user reference/assumption;
missing is not zero. Explicit reviewed zero inputs are permitted. User-declared
and synthetic cost scenarios are labeled separately and do not assert provider
or firm fees. Keep risk at/below 1% and enter a positive safety buffer. Budget is
`max(0, min(equity × risk% / 100, daily_remaining − buffer, EOD_remaining − buffer))`.
Loss per contract is `abs(entry − stop) × point_value + slippage_points × point_value + fees`.
Prices align to the 0.25 tick. Size is the integer floor of budget/loss, capped
at 20. A zero size can be an otherwise calculated worksheet. Gaps and actual
fills may exceed this estimate; this is not execution permission or a signal.

**A positive newly calculated size requires a confirmed flat account.** Existing
position/order schemas lack their stop/contingent risk. Open exposure therefore
produces UNKNOWN for this full worksheet; the unchanged cap-only check still
counts all exposure. Missing coverage, unconfirmed costs/account or stale open
sessions are insufficient. Breaches, outside-window/revision/term mismatches are
blocked; malformed or inconsistent money/timing is rejected. Contract validation
checks the dated identifier format; this arithmetic worksheet does not independently
certify contract availability, expiry calendars, market-data quality or strategy edge.

## Personal counting rules

- Only dated MES and MNQ contracts are eligible. Mini contracts, other roots and
  malformed existing contract identifiers block the check instead of being ignored.
- Add all open-position quantities and all working-order quantities, across
  directions and expiries. There is no netting, OCO deduction, or assumption that
  an order reduces a position. This conservative convention was approved by the user.
- A proposed additional quantity must fit the single shared ceiling. For example,
  10 MES positions and 9 MNQ working orders leave room for 1 Micro. A request for
  2 more is blocked. At 20, no additional contract fits.
- Entry checks use **07:00 inclusive to 14:00 exclusive UTC/GMT**, independent of
  local DST. This window is a personal preference, not an exchange holiday calendar.
- A fresh, open journal session and a complete, human-confirmed account observation
  with net costs are required. The existing 1,800-second observation ceiling is
  reused; it is not a calibrated production service guarantee.
- Missing or stale evidence produces UNKNOWN. Invalid evidence is blocked or
  rejected. No prices, commissions or missing positions are invented. Net fees
  already present in the journal are not deducted a second time.

Exceeding the cap produces information for human review. The API cannot reduce,
cancel, liquidate or place an order. Existing firm-policy and structural-risk
checks continue independently. The personal check does not require verified firm
progression bands, and its result cannot substitute for a firm allowance.

## Manual API use

Use the existing isolated assistant and its existing authentication. The preceding core increment did not add a dashboard panel. The separately
approved dashboard increment below adds manual inputs without changing the API,
`.env`, account policy or execution permissions.
Create/update a manual journal through the existing evaluation endpoints, including
the complete `account` observation in its current open session. Prices and PnL
must come from your own reported evidence; do not copy synthetic fixtures into
an actual account.

Send an authenticated request to:

```text
POST /assistant-api/evaluations/{existing-account-id}/user-policy-check
Authorization: Bearer <your locally stored assistant access token>
X-Advisory-Client: dashboard
Content-Type: application/json
```

Example request shape (contract identifier is illustrative):

```json
{
  "instrument_id": "MES",
  "contract": "MESZ26",
  "additional_contracts": 1
}
```

You can include `expected_account_revision`, the 64-character digest returned by
a previous check. A changed journal then blocks the stale request. Every new
request reads a single durable journal snapshot and recomputes the check. No
personal assessment is stored and no persistent verification cache is added.

The response includes:

| Field | Meaning |
| --- | --- |
| `label`, `origin`, `scope` | USER POLICY, user-defined, exposure check only |
| `maximum_micro_contracts` | Fixed 20; cannot be overridden by request input |
| `gross_micro_contracts` | Reported positions plus working orders; null if incomplete/unsupported |
| `remaining_micro_contracts` | Remaining personal capacity only for WITHIN_CAP; 0 when BLOCKED, null when UNKNOWN |
| `state`, `reasons` | WITHIN_CAP, BLOCKED or UNKNOWN, with explicit reasons |
| `profile`, `sessions`, `account_revision`, `generated_at` | Captured evidence and computation identity |
| `firm_compliance`, `passing_probability` | NOT_ASSESSED and UNKNOWN |
| `trade_permitted`, `execution_enabled` | Always false |

Returned capacity is the shared remainder before the proposed addition; it is not
an independent allowance for each root. A successful response is a dated statement
about the captured reported snapshot, not ongoing permission. The public
`verify_user_policy_assessment` replays the captured projection each time and
rejects reconstructed results that disagree with their evidence. A matching
projection does not authenticate a broker statement or prove the truth of inputs.

No existing imports, signatures, evidence fields or financial arithmetic are
changed. The new schema cannot be parsed as an existing `PolicyAssessment`,
`PolicyRiskAllowance` or positive `RiskDecision`. The selected TCP50 policy retains
its independent unresolved-progression gate.
